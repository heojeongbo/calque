# Migrating

Coming from `protoc-gen-orm-ts` or `protoc-gen-orm-ent`. The annotation
vocabulary is the same, so your protos do not change. What changes is the
plugin entry, and what you have to be careful about is the database that already
exists.

## The principle: swap first, fix second

Two commits, not one.

**Stage 1 is a drop-in.** calque generates what the old generator generated,
byte for byte, including its bugs. The diff on the swap commit is the header
line and the import specifier. If anything else moved, that is the bug — not a
question of whether the new output is better.

**Stage 2 fixes things**, one commit per item, each reviewable on its own.

The reason to separate them is not neatness. It is that if the swap and the
fixes land together and something breaks, you cannot tell which one broke it,
and reverting gives up both.

## Why calque keeps bugs on purpose

The generated code describes a **stored schema**, and a stored schema that
already has data in it is not free to change.

The sharpest case is Dexie. A Dexie database is opened at a version, and
**a version cannot be lowered** — a browser already on the higher version throws
`VersionError` against code that asks for a lower one. So:

1. fixing a schema string changes the stored schema
2. which requires bumping `version(n)`
3. after which a rollback leaves every browser that opened the new version
   unable to open the old code at all

Which means fixing a generator bug makes the swap **unrevertible**. That is a
decision to take on purpose, with a migration plan, not something to smuggle
into a change whose whole claim is that nothing moved.

So `dexie.compat: orm-ts` is the default, it reproduces the bugs, and it warns
on stderr every single time it generates:

```
calque: apptest.User: index component "token_hash" is stored as "tokenHash"; the index is
declared under a name no row has, so it is never used
	compat: orm-ts is reproducing protoc-gen-orm-ts here. Set dexie.compat: none to fix
	it — that changes the stored schema and needs a Dexie version bump.
```

The same reasoning is why `Strict()` is false under compat. A backend that
refuses everything it cannot hold would, on an existing schema, generate
nothing — and "adopt this by first fixing every constraint" is not a migration
anyone performs.

## Stage 1: the swap

### TypeScript

```yaml
# before
  - local: [protoc-gen-orm-ts]
    out: src

# after
  - local: [go, run, github.com/heojeongbo/calque@latest]
    out: src
    opt: [config=calque.yaml]
```

```yaml
# calque.yaml
version: 1
targets:
  - {target: ts, backend: dexie}
ts:
  runtime: "@protobuf-orm/runtime"                        # keep the old specifier for now
  header: "// Code generated by protoc-gen-orm-ts. DO NOT EDIT."
```

Setting `header` and `runtime` to what the old generator emitted is what makes
the diff empty rather than merely small. Change them in stage 2, when the diff
is expected.

Then:

```sh
buf generate
git diff --stat        # expect: nothing
pnpm typecheck
pnpm test
```

If your `package.json` moves to `@heojeongbo/calque-dexie`, do it as its own
commit: it re-exports everything the old runtime did, and mixing a specifier
change into the swap makes the diff unreadable.

### Go

```yaml
  - local: [go, run, github.com/heojeongbo/calque@latest]
    out: gen
    opt: [config=calque.yaml, module=example.com/app, default_api_level=API_OPAQUE]
```

The `module=` and `default_api_level=` must match your protoc-gen-go entry
exactly. See [the Go target](targets/go.md).

The gate here is stronger than a diff, because ent expands the schema into the
physical database:

```sh
buf generate
go tool entgo.io/ent/cmd/ent generate ./oas/schema --target /tmp/entout
diff -u oas/ent/migrate/schema.go /tmp/entout/migrate/schema.go   # expect: empty
go build ./... && go test ./...
```

An empty `migrate/schema.go` diff means no column, index or foreign key moved,
which is the thing you actually care about.

The Go target replaces two plugins at once — `protoc-gen-orm-ent` and
`protoc-gen-orm-go` — and those emitted files carrying two different generator
names. `go.header` and `go.query_header` are what keep line 1 of each group
unchanged.

## Stage 2: what to fix, and in what order

Each of these is a measured divergence from
[docs/conformance.md](conformance.md). Take them one at a time.

**Cheap, no stored-schema change:**

| | |
|---|---|
| header and runtime specifier | `ts.runtime`, `ts.header`. Pure text |
| `import_extension` | if your build strips `.ts` with a post-pass, emit what you want instead |

**Needs a database version bump — plan the rollback before you start:**

| | |
|---|---|
| index spellings | `dexie.compat: none`. The index that was declared under a name no row has starts working |
| unique indexes | `compat: none` marks them `&`, so they start being enforced. If the existing cache holds rows that violate one, the upgrade fails — which is why the recovery below is not optional |

Plan the rollback *first*, because a Dexie version cannot be lowered and there
is probably nothing in the app that can recover from `VersionError`. If the
cache is write-through, discarding it is cheap enough to be the recovery:

```ts
database.version(4).stores({ ...schemas() });

database.open().catch("VersionError", async () => {
	await database.delete();
	await database.open();
});
```

Add that *before* the bump, or in the same change, and the bump stops being
one-way.

An upgrade function is usually not needed for this particular fix: the rows
already carry the property names the new indexes name, so the store fills them
from what is there.

**Needs a code change, not just a regeneration:**

| | |
|---|---|
| `_reconcile` always returning true | **fixed in `@heojeongbo/calque-dexie` v0.2.0.** Callers that check its result have never taken the `false` branch; upgrading makes those branches live for the first time |
| edges embedded rather than referenced | changes what a row contains |

## Turning the warnings into errors

When you have fixed everything a backend was warning about, make it strict:

```yaml
dexie:
  compat: none
```

or, to try it without committing:

```yaml
opt: [config=calque.yaml, dexie.compat=none]
```

From then on a schema asking for something the store cannot hold stops the
build, naming the index and saying what to do. That is the state calque is for;
compat is the ramp to it.

## A note on the two generators disagreeing

If you are running both — Go on one tree and TypeScript on another, from the
same protos — check the entity counts before you start. In the deployment that
motivated calque, one pipeline emitted 13 entities and the other 19, from
schemas nobody had compared, and neither raised anything. The result was tables
in the browser database backed by no server-side entity of the same name.

One calque config describes one generation, and every target listed in it sees
the same entities.
