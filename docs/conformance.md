# What two targets have to agree about

calque generates ORM code for more than one language from one annotated schema.
That is only worth doing if the results agree, so this is the list of things
they have to agree about, and it is calque's acceptance criteria rather than a
wish list.

Every item was measured, not imagined. The two generators that came before
calque — `protoc-gen-orm-ent` (Go, on ent + SQL) and `protoc-gen-orm-ts`
(TypeScript, on Dexie + IndexedDB) — are driven from the *same* proto tree in a
production deployment, so where they disagree is observable. Where an item says
"today", it means those two generators as of this measurement.

## How this was measured

Both pipelines were regenerated from a clean checkout with the toolchain each
pins (buf 1.66.0), and both test suites were run.

**Both regenerate byte for byte.** Zero drift on either side. The committed
output is exactly what the pinned toolchain produces, which means every
divergence below is a property of the generators and not of a stale checkout.

The test posture is lopsided, and it matters for how much weight to put on each
side of a comparison:

| | result |
|---|---|
| Go, ORM round-trip (`server/core`, `server/schd`) | **102 tests, all pass** — proto → ent → SQLite → ent → proto, over real gRPC, against an in-memory database |
| Go, whole module | 2 failures, both unrelated to the ORM and pre-existing (a `42 != 43` assertion; a test opening a hardcoded container path) |
| TypeScript, ORM | **no tests exist** — no `fake-indexeddb`, no Dexie test, nothing touching the generated tables |
| TypeScript, everything else | ~2000 pass, 8 fail — timezone formatters, a canvas mock, a corpus invariant. None ORM |

So on the Go side "it works" is demonstrated. On the TypeScript side it is
asserted. Several items below are latent precisely because nothing exercises
them.

---

## 1. Coverage — the same schema must produce the same entities

**Today they do not.** The Go pipeline emits 13 entities; the TypeScript
pipeline emits 19. The extra six are entities the Go pipeline deliberately
excludes from its input, and no error is raised on either side — each generator
is simply pointed at a different subset and neither knows the other exists.

The result is tables in the browser database backed by no server-side entity of
the same name.

**calque:** one config describes one generation. If two targets are listed, they
see the same `Schema.Sources()`. Excluding an entity from a target is a thing
the config says out loud, and a target that emits an entity another target does
not is reported, not discovered later.

## 2. Operations — a declared RPC must be generated or refused

**Today they do not agree.** From `rpc: {crud: true}`, Go generates `Add`,
`Get`, `Patch`, `Erase`. TypeScript generates **`get` only**. `List` is
hand-written per entity on the Go side, and on the TypeScript side the gap is
licensed at the type level by `implements Partial<XServiceClient>` — which is a
way of saying "some methods are missing" that no compiler will ever complain
about.

(Note also that `Apply` is documented upstream but is not in fact generated by
either.)

**calque: not yet.** Both targets still emit their operations directly, so
TypeScript still emits `get` only. This is the one item on the list calque does
not answer.

There was an answer half-built — a plan AST in the core, deriving an entity's
operations from its schema, on the reasoning that which operations exist is a
property of the schema and not of a language. It had tests and no callers, and
it was deleted rather than left in place, because a design nothing exercises
stops being a design. It gets rebuilt with the target that consumes it. Until
then this row is open, and saying so is the point of the document.

## 3. Uniqueness — a constraint nobody asked the store for

This is the sharpest divergence, the one with a paper trail, and the one this
document got wrong twice.

A unique index over a field and an edge is enforced by ent as a real unique index
on the foreign-key column. `protoc-gen-orm-ts` emitted the same declaration as
`[alias+tenant.id]` — no `&` — so **the uniqueness was silently dropped**.
Nothing warned.

It has already cost something. The consuming application carries a database
version bump whose comment records restoring a compound index that had been
dropped "while the `sequence` index was briefly non-unique". That is this exact
failure, found in production and fixed by hand.

**What this document used to say** was that Dexie has no unique form of a
compound index, so the constraint was unholdable and the only honest thing to do
was refuse. That was an inference from the output, and it was wrong. Dexie
decides `unique` from `&` and `compound` from whether the key path is an array,
independently; nothing forbids the combination; and `createIndex` receives
`unique: true` with the array key path, which IndexedDB enforces. `&[a+b]` works.
It is measured in `ts/packages/dexie`: two rows with the same pair, and a
`ConstraintError`.

So the constraint was never unholdable. It was unasked for.

**calque:** every part of a Dexie schema string comes from `Entity.Keys()`, which
yields only unique elements, so every part is marked `&` — `&alias` for one
member, `&[alias+tenant.id]` for several. One assertion checks it, which is what
the earlier version of this item lacked.

A store that genuinely cannot hold a constraint still stops the build, and
`dexie.accept` is how a cache says it will live with one the store of record
holds instead. That mechanism was built for the nine indexes described above,
and none of them needed it.

## 4. Names — a store key and a message property are different names

The predecessor computes an index name from the proto field name and the query
key from the JSON name. For a single-word field these coincide. For a
multi-word field they do not, and the generated code declares an index under one
spelling and queries it under the other:

```ts
export const Schema = "&id,&token_hash" as const;   // declared: proto name
...
const q = { tokenHash: k }                          // queried: JSON name
return this._query(t => t.where(q).first());        // → SchemaError at runtime
```

Two entities in the measured schema are in this state. Both are latent only
because the generated lookup has no call site anywhere — the moment anyone wires
one up, it throws.

This is the third instance of one bug. The same mismatch was fixed once in the
reference-descriptor emitter (`fix: value jsonName`, June 2026), and the schema
builder and query emitter still disagree.

**calque:** `ProtoName`, `ValueName`, and `StoreName` are distinct Go types
(`schema/name.go`). A `ValueName` comes from the descriptor's `JSONName()` and
is never computed. Putting one where another belongs does not compile, so this
bug cannot be written a fourth time.

**Fixed.** `dexie.compat: none` spells an index component the way the row
carries it, and the deployment this was measured against has taken the Dexie
version bump that changing a stored schema requires. Two indexes that had never
matched a row now exist.

Worth recording how nearly it was not fixed. The types stopped the bug being
*computed* wrongly, and it survived anyway in the two places that never asked
for a name at all — the primary key and an edge's target key were written
straight from `.Name()`. Every key in the measured schema is `id`, where the two
spellings coincide, so those two would have gone on being wrong for the first
schema with a multi-word key. Distinct types catch a conversion; they do not
catch not doing one.

## 5. Optimistic locking — the same version field, two different guarantees

Go implements a genuine compare-and-swap, folded into the UPDATE so it is atomic
without a transaction: the caller's version becomes a `WHERE` clause, an absent
version is `InvalidArgument`, `<field>_force` drops the clause, and zero rows
affected is `FailedPrecondition`.

TypeScript implements last-writer-wins by comparing timestamps, and its
`_reconcile` **discards the outcome of its own comparison** — the `false`
returned inside the transaction never reaches the caller, so the method always
answers `true`. The consuming cache reads that answer:

```ts
const ok = await table._reconcile(v);
if (!ok) continue;      // never taken
```

So one target refuses a stale write and the other believes every write landed.

**calque:** the Go target implements the compare-and-swap, folded into the
UPDATE so it is atomic without a transaction, and distinguishes "gone" from
"someone got there first" with two error codes. On the TypeScript side
`_reconcile` returns an outcome the caller can act on as of runtime v0.2.0 —
the comparison and the write are in one transaction, so the answer is not stale
by the time it is returned. `query.Plan.Guard` carries the same compare in the
neutral IR, and is not yet read by either target.

## 6. Edges — reference, not copy

Go stores an edge as a foreign key to the target's key. TypeScript embeds the
whole target message in the row and indexes a nested key path into the copy.
The same proto therefore has different key semantics depending on the store, and
the embedded copy has no mechanism to be refreshed when the target changes.

There is a second-order cost: the embedded write is generated without a presence
guard, so an absent edge throws while dehydrating. The consuming application
works around it by requiring every key edge in every caller's field mask, and by
wrapping each row in `try`/`catch` — a workaround documented in a comment rather
than fixed in the generator.

**calque:** edges are stored as a reference to the target's key. Embedding is
opt-in per edge, not the default. This is also the choice that makes the two
targets agree rather than merely coexist.

## 7. Keys — where the two actually already agree

Worth recording, because it is the one thing that came out right by accident and
calque must not regress it.

A `bytes` field typed `TYPE_UUID` is 16 raw bytes on the wire in both targets.
On disk, Go writes the hyphenated lowercase string (via `google/uuid`'s
`driver.Valuer`) and TypeScript writes the same hyphenated string (because
IndexedDB cannot index a byte array). **The two databases hold the same
representation.**

They differ on invalid input: Go rejects anything that is not 16 bytes with
`InvalidArgument`, while one of the Go helper paths silently maps a bad id to
the zero uuid.

**calque:** the codec is named by the backend (`CodecUUIDString`,
`CodecUUIDBytes`) and implemented by the runtime adapter, so the choice is
explicit per store rather than incidental. Rejecting a malformed key is part of
the adapter contract, and the conformance suite asserts the same rejection from
every backend.

## The shape of the conformance suite

Items 1–7 become executable checks that any target/backend pair must pass:

| check | asserts |
|---|---|
| coverage | every `Schema.Sources()` entity is emitted by every configured target |
| operations | every declared RPC has a plan, and every plan is emitted |
| uniqueness | a constraint the backend cannot hold is refused at generate time |
| names | a store path and a value path are never interchanged |
| locking | a stale write is refused, and the caller is told |
| edges | an edge round-trips as a reference; an absent optional edge does not throw |
| keys | a key round-trips byte-identically; a malformed key is rejected |

The suite is written once against the contract and run against every backend,
which is what makes a second backend cheap and a second language honest.
