# Configuration

Two places say something: `calque.yaml`, which describes the generation, and the
plugin's `opt=` string, which says where that file is and lets a build vary one
setting without a second file.

## `calque.yaml`

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/heojeongbo/calque/main/calque.schema.json
version: 1

targets:
  - {target: ts, backend: dexie, out: ts}
  - {target: go, backend: entsql, out: go}

ts:
  runtime: "@heojeongbo/calque-dexie"

dexie:
  compat: orm-ts
```

The modeline is worth pasting. `calque.schema.json` ships in the repository and
gives an editor completion and validation for everything below.

### Top level

| key | required | |
|---|---|---|
| `version` | yes | must be `1` |
| `targets` | yes | at least one entry |
| anything else | | a section for a target or a backend to claim |

`version` is required rather than defaulted so that a future format change
reports *"this calque understands version 1"* instead of a cascade of
unknown-key errors about keys that were perfectly valid in the version you
wrote.

### `targets[]`

| key | required | default | |
|---|---|---|---|
| `target` | yes | | a target registered in the binary being run |
| `backend` | yes | | a backend registered in the binary being run |
| `out` | | `""` | a subdirectory of the output root buf gives the plugin |
| `name` | | `target` | disambiguates two entries with the same target |

All three names must match `^[a-z][a-z0-9-]*$`.

`out` is a *subdirectory*, not an output root: buf owns that and hands it to the
plugin. An absolute path, or one containing `..`, is refused at parse time.

`name` is a label, not a section key. Options are claimed under the target's own
name, so two entries running `ts` read the same `ts:` section. Naming them apart
is for diagnostics and for saying which entry emitted which file — if two
entries claim the same output path, the error names both.

### Registered targets and backends

| target | backends it accepts |
|---|---|
| `ts` | `dexie` |
| `go` | `entsql` |

A pairing a target does not accept is refused before anything is configured,
naming what it does accept. A target's runtime has adapters for specific stores;
selecting one it has no adapter for should not produce a package that imports
something nobody wrote.

### `ts:`

| key | default | |
|---|---|---|
| `runtime` | `@heojeongbo/calque-dexie` | the module generated code imports |
| `header` | `// Code generated by calque. DO NOT EDIT.` | first line of every file |
| `import_extension` | `""` | appended to relative imports — `.js` for NodeNext |

### `go:`

| key | default | |
|---|---|---|
| `schema_dir` | `schema` | where ent schema types go, under the proto's Go package |
| `ent_dir` | `ent` | where conversion helpers go — they are methods on ent's types, so they have to live there |
| `bare_dir` | `server/bare` | where the generated servers go |
| `header` | `// Code generated by calque. DO NOT EDIT.` | first line of every file |
| `query_header` | same as `header` | first line of `query.g.go` and `store.g.go`, for a drop-in whose two file groups came from two different upstream generators |

The Go target also needs the flags protoc-gen-go was given; see
[the Go target](targets/go.md).

### `dexie:`

| key | default | values | |
|---|---|---|---|
| `compat` | `orm-ts` | `orm-ts`, `none` | reproduce `protoc-gen-orm-ts` bug for bug, or spell things correctly |

`compat` also decides whether a capability shortfall stops the build. Under
`orm-ts` it is a warning on stderr; under `none` it is an error. That is not two
settings sharing a switch — a generator reproducing an older one has to keep
generating, or adopting calque on an existing schema would produce nothing at
all. See [Migrating](migrating.md).

### `entsql:`

| key | default | values | |
|---|---|---|---|
| `dialect` | `sqlite` | `sqlite`, `postgres`, `mysql` | decides the capability set |
| `table` | | map of entity full name to table name | renames a physical table |

`dialect` is a capability question, not a formatting one: MySQL has no partial
index, so an entity that erases softly cannot have a unique index covering only
its live rows, and Postgres caps a compound index at 32 members.

```yaml
entsql:
  dialect: postgres
  table:
    apptest.User: users
```

The default table name is the entity name lower-cased whole — `PosePreset`
becomes `posepreset` — which is what pins it against ent's own default of a
snake-cased plural.

### Typos

Both kinds are loud, and they are caught by different things:

- **inside a section**, decoding is strict, so `runtimee:` fails naming the
  section.
- **the section name itself**, which strict decoding cannot see, is caught after
  every target and backend has had its chance to claim. Anything left over is an
  error listing what this build does understand:

```
calque.yaml: nothing understands "dexei"
	this build knows: dexie, entsql, go, targets, ts, version
```

## Plugin options

```yaml
plugins:
  - local: [go, run, github.com/HeoJeongBo/calque@latest]
    out: gen
    opt: [config=calque.yaml, quiet=true]
```

| opt | |
|---|---|
| `config=<path>` | where `calque.yaml` is, resolved from where `buf generate` ran |
| `manifest=<path>` | also emit the list of files this run produced |
| `quiet=` | turn off progress reporting. `true`, `1`, or bare `quiet=` |
| `<section>.<key>=<value>` | override one setting on top of the config file |

Anything else is refused, naming what is understood — except the options
protoc-gen-go takes, which are passed through (below).

With no `config=`, calque looks for `calque.yaml` then `calque.yml` beside the
working directory. A missing file names the absolute path it looked for, because
*"no such file: calque.yaml"* is unhelpful when the plugin's working directory
is not the one you were thinking of.

A value containing a comma is unrepresentable. That is protoc's parameter
format, not calque's choice, and a config path with a comma in it says exactly
that rather than arriving later as a mysteriously missing file.

### Overrides

```yaml
opt: [config=calque.yaml, dexie.compat=none, ts.import_extension=.js]
```

An override is applied when the section is claimed: the file's own section is
decoded first and the override lands on top. So the command line wins, and it
works for a section the file never wrote — which is the case that comes up, a
minimal config and a build that varies one thing.

The value is read as yaml, so `x.n=2` and a file saying `n: 2` mean the same
thing. Text yaml cannot read is the text itself, which is what makes
`ts.runtime=@scope/pkg` work.

Dots nest, so a map is reachable: `entsql.table.apptest.User=users`.

Mistakes are reported as the option you typed:

```
calque: opt dexie.compaat=none: unknown field "compaat"
```

and an override to a section nothing claims is reported like any other
misspelled section — the command line is not a way around that check.

### protoc-gen-go's options

The Go target builds its view of Go names from the same parameter string
protoc-gen-go is given, so these pass through untouched: `paths`, `module`,
`annotate_code`, `default_api_level`, and any `M<file>=<import>` or
`apilevelM<file>=<level>`.

Keeping calque's buf entry a copy of the protoc-gen-go entry is the point. Two
entries that disagree would generate Go referring to identifiers the other did
not create — loudly, at compile time, rather than quietly reading the wrong
field.

## Progress

calque reports what it is doing on **stderr**, because stdout is the response
protocol: a protoc plugin that prints anything to stdout has corrupted its own
output. buf shows a plugin's stderr, so this reaches you.

```
calque: 13 entities, 2 targets
calque:   ts  53%  (7/13) Robot
calque: [1/2]  50%  ts → dexie  19 files  (45ms)
calque: [2/2] 100%  go → entsql  42 files  (1.2s)
calque: 61 files, 1.3s
```

Whole lines, never a carriage return. Under buf, stderr is a pipe rather than a
terminal, so a spinner overwriting one line would leave the build log full of
`\r` and unreadable. The percentage goes inside the line instead.

`quiet=true` turns this off. It does **not** turn off warnings — a warning is a
fact about the result and progress is a convenience, and putting them behind one
switch would mean `quiet` could hide a constraint the store cannot hold.

## Manifest

```yaml
opt: [config=calque.yaml, manifest=calque.manifest]
```

```
# Generated by calque. Every file this run produced.
# Anything else under the output root is stale.
ts/apptest/client.g.ts
ts/apptest/db.g.ts
...
```

A plugin can only add files — it is never told the output root and buf may be
writing into an archive — so pruning what a previous run left behind is the
build's job, and this is what it prunes against.
