# The command line

buf runs calque with an **empty argv** — the parameter arrives inside the
`CodeGeneratorRequest`, and stdin and stdout are the protocol. So no subcommand
means *serve the plugin*, and everything below is for a person.

```sh
calque                  # what buf does: a request on stdin, a response on stdout
calque config [flags]   # read calque.yaml and say what this build makes of it
calque targets          # the targets and backends this binary knows
calque version          # which calque this is
```

None of the subcommands reads a request, and none of them generates anything.

Typing `calque` at a terminal says so rather than rendering a
`CodeGeneratorResponse` on it: protoc and buf always send a request, so an empty
stdin means there is no build.

## `calque config`

```sh
$ calque config -c calque.yaml
/app/calque.yaml
  version 1
  target  ts        ts → dexie
  target  go        go → entsql

sections
  dexie  (file)
    compat: orm-ts
    accept: [binary_key]
  entsql  (defaults only)
    dialect: postgres
    table: {}
  go  (file)
    ...
  ts  (CALQUE_TS_IMPORT_EXTENSION)
    runtime: "@heojeongbo/calque-dexie"
    header: // Code generated by calque. DO NOT EDIT.
    import_extension: .js
```

| flag | |
|---|---|
| `-c`, `--config` | where `calque.yaml` is. Without it, the same search a build does |
| `-o`, `--opt` | an override, as `<section>.<key>=<value>`. Repeatable |

It is `gen.Run` with the generating taken out: resolve every target and backend
name, let each claim its options, refuse whatever is left. That is where all the
config errors live, so this reaches them **without a proto tree, without buf,
and without waiting for a codegen run to fail**.

What it prints is the *effective* configuration rather than the file's half of
it. `entsql` above appears with its dialect even though the file never mentioned
it, because what is shown is the value the backend decoded into after applying
its own defaults. The parenthesis says where each section's values came from, in
the order they were applied.

It exits non-zero on a bad config, where the plugin would put the same message
in `response.error` and exit 0. Different callers: buf needs to print it, and a
person at a terminal needs an exit code.

A section is listed even when nothing configured it, because "what will this
build do" includes the parts nobody said anything about.

## `calque targets`

```sh
$ calque targets
target   go        entsql
target   service   storeless -- takes no backend
target   ts        dexie
backend  dexie
backend  entsql
```

The registry is fixed when the binary is built and has no other observable
form: before this, the only way to learn it was to misspell a target and read
the error. For a fork that added one, this is how you confirm the composition
took — and it is where you find out which targets are storeless, and therefore
which entries take no `backend`.

## `calque version`

```sh
$ calque version
calque v0.7.0
```

Read from the binary's build info, not from a number written into the source.
`docs/versioning.md` defines the plugin version as the git tag and the Go module
version, and for the documented invocation —
`local: [go, run, github.com/heojeongbo/calque@v0.7.0]` — that is exactly what
the module proxy resolved. A release-time constant would be a fourth number in
a document about three, and the only one that could disagree with the tag buf
actually ran.

A local `go build` has no module version, so it reports the revision the
toolchain stamped and whether the tree was dirty.

## Extending it

`cmd.NewCmdRoot` takes a registry, so adding a target does not need a fork; see
[Extending](extending.md). Below the command tree, `plugin.Serve` is the
request-in response-out door and takes no argv at all.
